## EXECUTIVE SUMMARY

This audit report provides an objective, evidence-based verification of all technical, mathematical, and statistical claims made in the Paventra project documentation, initial project report draft, and presentation deck. Every claim has been traced directly to source code, data fixtures, and reproducible terminal execution.

### Key Audit Highlights:
1. **Rule Base Count Discrepancy:** The code in `backend/app/services/prioritization/fuzzy_engine.py` implements **23 rules**, not the widely claimed **22 rules**. Rule 23 (`ctrl.Rule(time_days["very_long"] & traffic["high"], priority["high"])`) was present in the code but omitted from the academic specification tables and logged as 22 rules.
2. **Benchmark Provenance:** The 250-record maintenance benchmark (`analytics/fixtures/soft_computing_maintenance_benchmark.csv`) is **100% synthetic**, generated programmatically via `generate_benchmark_dataset.py` (seed 101). It contains **zero** real-world municipal maintenance outcomes and **zero** independent expert ground-truth labels. The "expected" fuzzy scores in the benchmark were generated by running the exact same fuzzy engine being evaluated.
3. **Statistical Verification:** Recomputing metrics directly from the 250 records confirmed the reported mean fuzzy score (**72.18**) and mean baseline score (**58.30**), as well as the escalation rate (**84.8%**). However, the reported standard deviations (claimed 13.42 and 11.87) were incorrect; actual population standard deviations are **15.08** and **11.21**. Furthermore, the priority tier counts reported in previous documentation differed significantly from actual code execution.
4. **Safety Override Claim Contradicted:** The claim that *"the Mamdani FIS guarantees a priority score $\ge 78.0$ in 100% of high safety-hazard scenarios ($U \ge 8.0$)"* is **CONTRADICTED BY SOURCE**. In the benchmark itself, 12 records with $U \ge 8.0$ scored below 78.0 (minimum: 53.55). In mathematical stress tests, a minor defect ($S=1.0$) with critical safety hazard ($U=10.0$) yields a defuzzified score of **35.25** (`MEDIUM`), because Rule R13 maps Low Severity + High Safety to `Medium-High`, which defuzzifies below 40 when combined with low-priority rules.
5. **Worked Example Falsification:** The Chapter 1 worked example ($S=9.0, T=1.5, D=1.0, U=10.0$) claimed a linear score of 61.50 and a fuzzy score of 92.4 (`CRITICAL`). Actual execution of the codebase yields a linear score of **59.61** and a fuzzy score of **71.39** (`HIGH`).
6. **Edge-Case Logic Flaw Discovered:** In `fuzzy_engine.py`, the helper function `_calculate_tri_membership()` returns `0.0` at exact domain boundaries ($x=0.0$ and $x=10.0$) for left/right shoulder sets due to strict `<` inequality logic. While `scikit-fuzzy` simulation computes correctly internally, the UI/API membership activation dictionary returns all zeros at domain extrema.
7. **Computer Vision Provenance:** The YOLOv8 model weights (`rdd2022_yolov8n.pt`) are a pretrained checkpoint downloaded from Hugging Face (`dronefreak/rdd2022-yolov8n`). The local dataset directory contains only 10 synthetic sample images; full training on 47,000 images was not performed locally.
8. **Automated Test Suite Verified:** The backend pytest suite was executed independently: **49 tests passed in 36.35s** with zero failures.

### 2.4 Discovery of Boundary Condition Defect in `_calculate_tri_membership()`
Inspection of lines 112–120 in `fuzzy_engine.py`:
```python
def _calculate_tri_membership(x: float, a: float, b: float, c: float) -> float:
    if x <= a or x >= c:
        return 0.0
    if a < x <= b:
        return (x - a) / (b - a) if b != a else 1.0
    if b < x < c:
        return (c - x) / (c - b) if c != b else 1.0
    return 0.0
```
- **The Defect:** When $x = 0.0$ for Left-Shoulder `low` ($a=0, b=0, c=4$), the condition `x <= a` evaluates to `0.0 <= 0.0` (True), returning `0.0` instead of `1.0`. Similarly, when $x = 10.0$ for Right-Shoulder `critical` ($a=8.5, b=10, c=10$), `x >= c` evaluates to `10.0 >= 10.0` (True), returning `0.0`.
- **Impact:** `scikit-fuzzy`'s internal C/Cython simulation (`fuzz.trimf`) handles these boundaries correctly during inference. However, `evaluate_all_memberships()`, which formats the `membership_activations` dictionary for the UI inspector and API JSON responses, displays `0.0` for all membership sets when inputs are exactly at domain endpoints ($0.0$ or $10.0$ or $365.0$).

  - `inputs.severity >= 8.5` $\to$ "Critical damage extent"
  - `inputs.safety_urgency >= 7.5` $\to$ "High safety / pedestrian hazard"
  - `inputs.traffic_exposure >= 7.0` $\to$ "Heavy traffic exposure"

# AUDIT 3 — SAFETY OVERRIDES & BASELINE BENCHMARK CLAIMS

### 3.1 Linear Baseline Formula & Unit Normalization
The baseline function (`fuzzy_engine.py`, lines 96–110) implements:
$$P_{\text{linear}} = 10 \times \left( 0.35 \cdot S + 0.20 \cdot T + 0.20 \cdot D_{\text{norm}} + 0.25 \cdot U \right)$$
where:
$$D_{\text{norm}} = \min\left( \frac{\text{time\_unresolved\_days}}{180.0}, \, 1.0 \right) \times 10.0$$

#### Discrepancies Found in Baseline Documentation:
1. `architecture.md` (line 149) specifies: $10 \times \min(10, \frac{\text{days}}{7})$.
2. `soft_computing_specification.md` does not state the normalization denominator.
3. The actual code normalizes over **180 days** ($D_{\text{norm}} = \frac{D}{18} \in [0, 10]$).

### 3.2 Falsification of the "100% Safety Guarantee ($\ge 78.0$)" Claim
The previous report and academic specification claimed:
> *"In 100% of high safety-hazard scenarios ($U \ge 8.0$), the Mamdani FIS guaranteed a priority score $\ge 78.0$ regardless of traffic density, completely neutralizing the linear model's traffic dilution vulnerability."*

#### Empirical & Theoretical Disproof:
1. **Benchmark Evidence:** In the 250-record benchmark, 62 records have $U \ge 8.0$. Of these, **12 records have a fuzzy score below 78.0**. The minimum score in this subset is **53.55** (Record `PAV-03A8DFB1`, inputs: $S=5.8, T=2.2, D=1.2, U=8.1$).
2. **Stress Test Case:** When evaluated with $S=1.0$ (Low Severity), $T=1.0$ (Low Traffic), $D=0.0$ (Short Time), and $U=9.0$ (High Safety Urgency):
   - Linear Baseline Score: **28.00**
   - Actual Mamdani Fuzzy Score: **35.25** (`MEDIUM`)
3. **Mathematical Cause:** In the rule base, Rule R13 specifies:
   `IF Severity IS Low AND Safety IS High THEN Priority IS Medium-High`
   The consequent is `Medium-High` ([45, 60, 75]), not `Critical` or `High`. When defuzzified alongside active low rules (R18, R19, R21), the centroid pulls the score down to 35.25.
4. **Correction Required:** The system **does not guarantee** a score $\ge 78.0$ or a `CRITICAL` tier for all $U \ge 8.0$. It escalates safety priority relative to the baseline ($+7.25$ points), but the final tier remains conditioned on damage severity.

### 3.3 Falsification of Chapter 1 Worked Example
The previous report presented the following worked example in Section 1.3:
- Inputs: $S = 9.0, T = 1.5, D = 1.0\text{ day}, U = 10.0$
- Claimed Linear Score: $61.50$ (`MEDIUM_HIGH`)
- Claimed Mamdani Score: $92.40$ (`CRITICAL`)

#### Actual Code Execution:
- Actual Linear Score: **59.61** ($0.35 \times 9 + 0.20 \times 1.5 + 0.20 \times 0.0556 + 0.25 \times 10 = 5.961 \times 10$)
- Actual Mamdani Score: **71.39** (`HIGH`)
- Actual Delta: **+11.78**
- **Cause:** Because $S=9.0$ has partial membership in High ($\mu=0.5$), Rule R07 (`severity[high] & traffic[low] -> priority[medium_high]`) activates alongside R01. The centroid of the aggregated surface defuzzifies to 71.39, not 92.40.
